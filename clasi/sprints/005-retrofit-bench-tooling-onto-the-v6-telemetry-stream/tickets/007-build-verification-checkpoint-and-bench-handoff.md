# Build/verification checkpoint and bench handoff

## Description

Mandatory, always-last ticket for any sprint touching build-eligible
source, per the standing convention sprint 008 established (see
`tools/DESIGN.md`'s "Build checkpoint triage" section and
`docs/design/design.md`'s "Host-vs-target language standard" section):
a green host suite is never evidence a change compiles for the real
target, so every such sprint ends with a real `tools/make_deploy.py`
run against the sprint's own combined final state. This sprint touches
build-eligible source in tickets 004 (C++), 005 (`testrig.ts`,
`make_deploy.py`), and 006 (`test.ts`) — this ticket is that
checkpoint, run after all six prior tickets have landed.

It is also this sprint's **bench-only-verification handoff ticket**,
per this sprint's own requirement that no ticket's acceptance criteria
may require a robot (precedent: sprint 004 ticket 005, sprint 006
ticket 006, sprint 007 ticket 008, sprint 008 ticket 006). This
ticket's own Acceptance Criteria are all satisfiable with network
access to the cloud compiler and no hardware; the real-hardware
end-to-end checks this sprint's `sprint.md` Success Criteria and Test
Strategy call for are captured below as a **handoff checklist** for a
stakeholder with bench access to run afterward, not as blocking
criteria for this ticket itself.

## Acceptance Criteria

- [ ] `uv run pytest` (full suite) passes as a precondition — this
      ticket's own build run should follow a green host suite, not
      substitute for one.
- [ ] A real, non-scratch run of `tools/make_deploy.py` against this
      sprint's own final state (tickets 001-006 landed) produces a
      flashable hex, with `classify_attempt()` reporting `SUCCESS`
      (after at most the documented bounded retry for a known-benign
      abort shape) and no compile diagnostic from any file.
- [ ] `testrig.ts` (ticket 005's fix) compiles clean via whatever
      mechanism ticket 005 added, with no type error — confirmed as
      part of this same checkpoint run, not assumed from ticket 005's
      own testing alone.
- [ ] `test.ts`'s two new named verbs (ticket 006) are present in the
      flashable hex's compiled output with no compile diagnostic.
- [ ] `test.ts` and `testrig.ts` are confirmed **not** combined into
      one hex — the flashable deploy hex's `files` still lists only
      `test.ts` (per ticket 005's own acceptance criteria; re-confirm
      here as part of the final combined state, not only in isolation).
- [ ] This sprint's `design/` overlay (`clasi/sprints/005-*/design/`)
      is re-read against what actually shipped across all six prior
      tickets; if any ticket's implementation deviated from what the
      overlay describes (verb names, module boundaries, the
      interpreter-resolution mechanism, etc.), the overlay copy is
      updated and its `.diff.md` regenerated by hand so every status/
      header line is true after this sprint closes and merges — the
      requirement stated at the top of this sprint's own planning
      brief. If no deviation occurred, note that explicitly (no edit
      needed, matching sprint 008 ticket 006's own precedent for this
      exact situation).
- [ ] `validate_design(overlay_dir=...)` (or the equivalent check) still
      returns `ok: true` after any such overlay updates.
- [ ] No robot, no flashing, no live telemetry capture is performed or
      required by this ticket's own acceptance criteria — producing a
      hex needs network access to the cloud compiler, not hardware.

## Bench handoff checklist (not this ticket's acceptance criteria — for a stakeholder with hardware access)

The items below are `sprint.md`'s own Success Criteria / Test Strategy
real-hardware checks. Record results here (or in a follow-up note) once
run; do not block moving this ticket to done on them, consistent with
this sprint's no-robot-in-acceptance-criteria constraint.

- [ ] `tour_run.py --tour world` against a real, awake robot (tick the
      kernel first, e.g. `RUN:straight:15`, before trusting
      `ready`/`connL`/`connR` — a freshly booted robot reports
      `ready=0 connL=0 connR=0` until something ticks it, which looks
      identical to a dead brick but is not one) produces a non-empty
      CSV and a non-trivial loss report (`dropped`/`loss_pct` in the
      `.meta.json` sidecar and console output).
- [ ] `require_stream()` is observed aborting a run for real when the
      robot is genuinely unreachable (wrong channel, radio off) —
      confirms the fail-loud guard against a live, imperfect radio
      link, not only synthetic test data.
- [ ] The retargeted ground-truth tools (`pivot_truth.py`,
      `truth_check.py`, `rotation_check.py`, `turn_sweep.py`,
      `otos_levercal.py`) each produce a real, non-silent response from
      the robot when run on the floor over radio — confirms ticket
      006's new named verbs work end to end, not only that the correct
      string is sent.
- [ ] `otos_bench.py` against `testrig.ts` (ticket 005's dispatch fix)
      produces a real response (e.g. `RUN:20` → `OID:<productId>`) on
      the zeguz rig — confirms the one-line dispatch fix works on
      real hardware, not only in the compiled-output sense ticket 005's
      own acceptance criteria cover.
- [ ] `tools/camproc.py`'s `ERR`-surfacing and stale-pose invalidation
      (ticket 003) are observed against a real camera daemon
      disconnect/restart, not only a simulated one.
- [ ] Flag any surprise here (a wire behavior, a timing issue, a
      vocabulary mismatch) as a new issue rather than silently working
      around it, per this project's standing practice.

## Implementation Notes

- Follow `tools/make_deploy.py`'s own triage exactly (see
  `tools/DESIGN.md`'s "Build checkpoint triage" section) — a BENIGN
  abort shape is retried once automatically; do not manually re-run
  past that without understanding why the triage itself did not
  already handle it.
- If a genuine compile failure surfaces here, it means either a prior
  ticket's own Acceptance Criteria were insufficient or something
  changed between that ticket's landing and this checkpoint — do not
  patch around it silently in this ticket; identify which prior
  ticket's change is responsible and fix it there (reopening if
  already marked done), consistent with this project's
  "tests that can fail" theme applied to the whole sprint.

## C++11 Gate Coverage

- **Inside the gate**: no new file is added by this ticket itself; run
  `tests/host/test_cxx11_syntax_gate.py` as part of the precondition
  full suite to confirm it still passes against tickets 001-006's
  combined final state.
- **Outside the gate**: this ticket's own subject IS the gap the C++11
  gate cannot close — it is what proves, for this sprint's own final
  state, that ticket 004's C++ changes and tickets 005-006's PXT
  changes actually compile and link for the real embedded target. It
  depends on tickets 001-006 specifically so it validates their
  combined final state, not each in isolation.

## Testing

- **Existing tests to run**: the full `uv run pytest` suite, as a
  precondition.
- **New tests to write**: none — this ticket's own verification is the
  real build itself; the bench handoff checklist above is deliberately
  outside `pytest`'s scope (it needs hardware).
- **Verification command**: `uv run pytest` (precondition), then
  `uv run python tools/make_deploy.py` plus ticket 005's
  `testrig.ts`-specific build/type-check invocation — record the
  resulting hex's path/size in this ticket's own notes on completion.
