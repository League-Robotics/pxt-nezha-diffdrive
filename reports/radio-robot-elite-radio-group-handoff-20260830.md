## Why this exists

As of 2026-08-30 a micro:bit's radio address is **derived from its
five-letter name** (`channel = 25 + 2·(N mod 25)`, `group = 1 + N div
25`, skipping 10). Spec: `pxt-nezha-diffdrive/docs/radio-addressing.md`
(on the sprint-025 branch there). Group 10 is now the one group the
assignment can never emit, because a hand-dialled relay `!C <ch>`
forces group 10 and must never collide with an assigned address.

Consequences already landed elsewhere:

- `radio-robot-lib` `eff85b7` (2026-08-30 09:40) stores BOTH halves per
  robot in `config/robots/*.json`: gopiv 47/60, togov 37/109, tovez
  55/108, vevov 37/43, zeguz 25/19, zetuv 27/21. Its commit message
  says the proto was updated "so a future regeneration reproduces it".
- `pxt-nezha-diffdrive/tools/make_deploy.py` injects `kChannel` and
  `kGroup` per robot from that config at deploy time (absent group →
  10 for legacy configs; a name-derived channel with no group is
  refused).
- Only **gopiv** is flashed to its new address (relay `!CG 47 60` →
  4/4 pong; `!CG 5 10` → silent — `pxt-nezha-diffdrive/captures/
  radio-addressing-20260830.md`). vevov/tovez/zeguz/zetuv are still on
  4/10 and 3/10.

The proto's old comment ("group is fixed at 10 to match the
RadioRelay") therefore became false, and elite is the *upstream* of the
generated schema that `radio-robot-lib` copies — so the proto is the
only correct place to fix it. Hand-editing a copy of the generated
schema (which lib did) is exactly what a regeneration would undo.

## Don'ts

- Don't hand-edit `robot_config.schema.json`, `robot_config_generated.py`
  or `*_pb2.py` — regenerate.
- Don't `!N <name>` an unmigrated board; use explicit `!CG`. `HELLO` is
  a session reset, not a liveness probe — use `PING`/`STATUS`.
- Don't treat a silent board as a dead board before checking which
  address the relay is tuned to. The whole point of this change is
  that "silent" now has a config cause.
